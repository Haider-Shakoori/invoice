# Backup and Restore Runbook

Invoice Drafts SaaS stores data in two places that must be recovered together:

1. the central commercial database
2. each tenant database plus that tenant's private files

A database-only backup is therefore not a complete backup.

## Creating a backup

Run:

```bash
php artisan invoice:backup
```

By default, bundles are created under `storage/app/backups/<timestamp>`. A private absolute location can be supplied:

```bash
php artisan invoice:backup --path=/srv/backups/invoice/pre-release-2026-09-28
```

The command creates:

- `database/central.sql`
- one `database.sql` per tenant
- each tenant's private storage files, including branding and generated PDFs
- `manifest.json`

Database dumps use a single-transaction MySQL dump and include routines, events, triggers and binary-safe values.

## Integrity verification

Immediately verify every bundle:

```bash
php artisan invoice:backup-verify /srv/backups/invoice/pre-release-2026-09-28
```

Verification checks every manifest entry for:

- expected path
- existence
- byte size
- SHA-256

The verifier also rejects unsafe traversal paths.

A backup is not considered valid until this command succeeds.

## Backup security

The bundle contains tenant-private business data.

Operational requirements:

- never place it below the public web root
- keep directories private to the deployment account
- encrypt off-host copies at rest
- transport backups over an encrypted channel
- restrict access to designated operators
- maintain a documented retention policy
- do not send a raw bundle through ordinary messaging/email

The backup command creates restrictive local permissions, but the external backup destination must enforce its own access controls.

## Controlled restore drill

Do not test a restore by importing over the live production databases. Use an isolated recovery host or isolated MySQL instance.

### 1. Verify the source bundle

```bash
php artisan invoice:backup-verify /path/to/bundle
```

Stop if verification fails.

### 2. Prepare clean recovery databases

Read `manifest.json` to identify:

- the central database name
- each tenant UUID/slug and database name

Create clean empty databases with the same names or an explicitly mapped recovery naming scheme. Keep the recovery instance inaccessible to production traffic.

### 3. Restore the central database

Example:

```bash
mysql --host=127.0.0.1 --user=<user> -p <central_database> < /path/to/bundle/database/central.sql
```

Do not import a full backup on top of a partially populated live database.

### 4. Restore each tenant database

For each tenant entry in `manifest.json`:

```bash
mysql --host=127.0.0.1 --user=<user> -p <tenant_database> < /path/to/bundle/tenants/<tenant-id>/database.sql
```

### 5. Restore tenant private files

The bundle contains each tenant's private file tree under:

```text
tenants/<tenant-id>/files/
```

Copy that tree into the tenant-specific storage root generated by the tenancy filesystem bootstrapper. Preserve file names and hierarchy; historical invoice snapshots can reference earlier branding assets and generated exports.

Do not merge one tenant's files into another tenant's root.

### 6. Configure the recovery application

Use recovery-only domain/database settings. Install the same application release that produced the backup before attempting an upgrade.

Then run:

```bash
php artisan invoice:doctor
php artisan invoice:migrate-tenants --dry-run
```

If testing upgrade recovery, take a second recovery snapshot before applying later migrations.

### 7. Validate recovery

Minimum validation:

- central operator authentication
- business/subscription records
- at least two tenant hosts
- tenant owner login
- customers
- invoice numbers/versions/totals
- branding assets
- existing PDF export re-download
- a new PDF export
- cross-tenant isolation
- scheduler/queue runtime

Compare representative totals and invoice counts with the source environment.

### 8. Record the drill

Record:

- backup timestamp
- manifest SHA-256
- recovery host
- restore start/end time
- operator
- tenants checked
- discrepancies
- corrective actions

A production backup policy is incomplete until a restore drill has succeeded using a recent bundle.

## Production recovery

When actual production recovery is required:

1. stop writes/queue workers
2. preserve forensic copies of the failed state
3. restore into clean databases/storage whenever possible
4. run the same recovery validation above
5. point traffic to the recovered environment only after readiness and tenant checks pass

Avoid destructive automated restore commands. Recovery should remain an explicit operator action because it replaces central and tenant data together.
